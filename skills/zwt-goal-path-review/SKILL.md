# ZWT 目标导向与路径审查

判断用户提出的做法是否是通往目标的合适路径。既避免把不必要的流程自动化，也避免越过真实约束替用户重定义需求；原方案合理时应明确保留。

## 先表达目标，再审查手段

- 第一项实质输出是基于上下文的最佳目标重述：用户真正希望得到什么结果、当前做法要解决什么痛点，以及哪些成功标准和边界已明确。将关键推断单独标明，不把自己的推荐路线写成用户原本的意图。
- 区分当前方法是用户明确要求保留的约束，还是可以讨论的初步设想。尊重已经确认的选择；不要仅因自己偏好别的技术，就反复要求用户重选。
- 目标已清楚时直接进入路径审查，不重做完整意图问诊或第一性原理拆解。缺少具体任务时才先问必要的问题；其余未知先给条件性分析，只追问会实质改变结论的关键点。

## 检查当前路径是否必要、可行

- 区分实现目标必需的环节、现有权限或业务规则要求的环节，以及可能仅由习惯或旧工具造成的环节。不要仅因步骤繁琐就认定它没有价值；审批、校验或数据转换可能承载必要约束。
- 从用户信息和已有证据核实关键前提：现有能力能否直接满足目标、数据口径是否一致、权限和接口是否可用，以及时间、投入、可靠性和维护要求。区分已知、推断和待确认条件；不能假定数据库直连、接口权限或替代功能已经存在。
- 必要时只读查看用户放在任务范围内的资料与实现，不扫描无关系统或连接未授权数据源。缺少证据不等于原方案错误，也不等于替代方案可行。

## 比较路径，不预设必须换方案

- 以原方案为比较基准，只提出确有依据、可能带来实质收益的少量替代路径。可以考虑复用已有能力、减少步骤或局部改进，不必开发新功能，也不必凑齐多个选项。
- 按本任务真正相关的目标达成度、正确性、权限与业务边界、交付速度、可靠性、持续维护及迁移成本比较；不编造收益数字，不用未经说明的评分制造精确感。
- 不固定技术优劣顺序：SQL、官方 API、统一导出、浏览器或鼠标自动化都可能适合。流程更短不代表总体更优；依赖不存在的权限、忽略业务规则或转移大量成本的方案不能冒充改进。
- 给出有判断的建议：**保留原方案、局部简化或更换路径**。只有替代方案的收益和可行性足以抵消切换成本时才推荐更换；原方案已经合适就明确说明理由，不为体现“顾问能力”强行挑错或推翻。
- 关键条件未知时给出条件性结论，指出什么新证据会改变推荐。即使原方案存在问题，也不因此默认任何替代方案都更好；不擅自扩大范围、放宽约束或承诺尚未验证的效果。

## 交付一份简短的路径判断

通常依次覆盖：

1. 用户真正要实现的结果，以及哪些方法或条件必须保留。
2. 当前路径依赖的关键前提，哪些有依据、哪些待确认。
3. 原方案与有价值的替代路径的实际取舍；没有值得比较的替代时直说。
4. 推荐保留、简化还是替换，理由及成立条件。
5. 最可能改变结论的未知项，以及一个最小确认或验证建议；没有重要未知时不强行追问。

篇幅与任务复杂度相称，可以合并表达，不额外生成完整产品规划、详细实施计划或长篇方案清单。

## 调用与讨论边界

- 仅在用户显式调用的当前轮次应用本流程。后续未再次调用时，不强制沿用其结构、继续审查路线或延续讨论限制；已确认的事实和用户修正仍可用于正常对话。
- 本技能只辅助讨论，不修改代码、文件、配置或数据，不执行方案、连接新服务或自动开展验证实验。输出的“下一步”是建议，不是行动授权。
- 用户认可目标、确认约束或表示建议不错，都不等于授权实施。用户明确转入实施并授权时，按其最新要求退出本讨论流程，不把已获得的授权重新变成确认门。
